Act II · Upgrade

Spring Boot 4.1 in one pass

Normally this is done one release at a time — there are 11 steps between Spring Boot 2.6 and Spring Boot 4.1, each with its own migration work. advisor upgrade-plan apply --squash 11 squashes all of them into a single pass — no manual code changes. Then it re-reads the app to capture the new SBOM.

At scale

One app was the demo. The portfolio is the job.

Customers run this against 100,000+ Java repositories: advisor-loop walks the whole estate every hour, opening pull requests and patching CVEs continuously.

Repositories100k+
Pass cadencehourly
Hand edits0

Two plain JVM processes — advisor-loop opens the PRs, advisor-verify answers them. No daemon, no scheduler: a pass runs, reports, and stops.

advisor-loop · one pass through the org

The loop

list repos → skip fresh PRs → build-config get → mapping loop → upgrade PR → patch PR
ORG/REPO ACTIVITY STATUS -------------------------------------------------------------------- dashaun-demo/spring-petclinic build-config get success dashaun-demo/spring-petclinic upgrade-plan get success dashaun-demo/spring-petclinic apply patch success dashaun-demo/spring-petclinic patch PR success 11 success, 1 fail, 1 skip

The output is the whole user interface: one line per activity, statuses only ever success, fail, or skip. A repo with a bot PR younger than 24h skips before advisor even runs — so re-runs are cheap.

advisor-loop · the steady state

What “best” looks like

  • Every repository on the latest Spring Boot, every dependency at its latest patch
  • Bot PRs recycled every hour — stale ones closed, branches deleted, nothing piles up
  • A mapping learned for one repository unblocks the whole portfolio
  • advisor-verify builds, deploys, and smoke-tests every PR automatically
  • Humans only do the part that matters: review and merge

The loop is the steady state — not a project, not a migration. Just the portfolio, always current.
